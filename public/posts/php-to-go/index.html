From PHP to Go: Eight Years Later

August 10, 2026 — #go, #career, #reflection — 479 words

My first commit was in PHP, in 2018. I was building a class project for a cloud computing course, and I didn’t know what I didn’t know. The code was messy, the architecture nonexistent, and I was proud of every line.

Eight years later, I spend most of my time in Go. Here’s how that happened and what I learned.

The Early Years: PHP and JavaScript

PHP was my entry point. It was everywhere, it was forgiving, and it let me build things that worked. I wrote CRUD apps, CMS plugins, and eventually a small SaaS. Alongside it, I picked up JavaScript and built frontend pieces with vanilla JS, then jQuery, then React.

The problem wasn’t the languages — it was that I was solving the same problems repeatedly, and each framework promised to fix it while introducing new ones. I was building on sand and calling it architecture.

The Middle: TypeScript, Svelte, Elixir

TypeScript was my first “aha” moment. Types weren’t bureaucracy — they were a conversation with your future self. I used TypeScript heavily, built a Svelte component library (connect-svelte-query), and briefly explored Elixir for its concurrency model.

Elixir taught me that fault tolerance and supervision trees were concepts I cared about deeply. But the BEAM ecosystem never quite clicked for the kind of work I was doing. I filed those lessons away.

The Pivot: Go

I picked up Go in 2024, reading Alex Edwards’ books and building small services. The language felt opinionated in a way I appreciated: one way to format code, one way to handle errors, one way to structure a project. It removed the “what should this look like?” question so I could focus on “what should this do?”

Go’s simplicity is often criticized as boring. I think that’s the point. Boring code is readable code. Readable code is maintainable code. Maintainable code is code you don’t hate working on at 2am when production is on fire.

What I Value Now

After eight years, here’s what I look for in a language or ecosystem:

  1. Clarity over cleverness. I want to read code like prose, not poetry.
  2. Tooling that works. go fmt, go test, go mod — they just work. No config files, no debates.
  3. Performance where it matters. Go’s goroutines and garbage collector are good enough for 99% of what I build, and the 1% is usually solvable with a few optimizations.
  4. Ecosystem maturity. The standard library is comprehensive. Third-party dependencies are usually well-maintained.

What’s Next

I’m not done learning. I’m currently exploring Odin for game development and keeping an eye on Zig for systems programming. But Go is my professional home for the foreseeable future, and I’m comfortable with that.

The languages I’ve used are just tools. What matters is what you build with them and whether you still understand your own code six months later.

Go passes that test for me.
